## Decisions

### Reporting Structure

- Report results and headline findings should appear near the top of the report.
- Technical attack parameters should be moved to an appendix.
- Interpretation layers (for example red/green indicators or "good/bad" assessments) are out of scope for the first release.
- Additional signposting should help users understand how reported metrics relate to significance thresholds.
- Report wording and structure can continue to be refined after the initial release.

### Metadata Catalogue

- The current catalogue contains placeholder descriptions generated during development.
- These descriptions require subject matter review before being considered release-ready.
- Hannah is not expected to approve the content of the catalogue definitions.
- Jim and Simon will review the catalogue definitions and determine whether they are acceptable.
- Long term, descriptions are expected to come from a central ontology rather than a manually maintained JSON file.

### Conversion Script

- The conversion script will be used as part of the first release process.
- The script should remain relatively decoupled from the core reporting workflow.
- Additional examples should be generated and tested using the conversion process.
- Direct generation of fully enriched report JSON files by individual attacks is considered future work.

### Release Process

The preferred sequence is:

1. Review and approve the catalogue/conversion-script pull request.
2. Regenerate example reports using approved catalogue content.
3. Complete remaining unit tests.
4. Raise a pull request for the reporting package.
5. Review report layout and presentation through the pull request process.
6. Prepare the first release.
